<em class="lead">什么能存活、什么是致命的，以及中间件相对于强制执行的位置</em>

有两类东西表面相似，但绝不可混淆：协议没有描述的材料，以及协议有描述但取值错误的值。前者是协议成长的方式；后者是缺陷。

## 规则 {#the-rule}

**不可识别的材料不是错误。畸形的已知值才是。**

- 一个本实现不识别的事件类型 MUST NOT 中止运行。
- 一个事件上未被描述的属性 MUST NOT 中止运行。
- 一个本实现不识别的并集成员——一种新类型的内容部分，或一个以它命名的结果——MUST NOT 中止运行。
- 一个协议*确实*描述了、却携带模式所拒绝的值的字段 MUST 是致命的：消费方 MUST 让运行失败，而不是修复、强制转换或忽略该值。

这个推理刻意是不对称的。一个实现发布之后新增的事件类型是在预期之中的——发送方更新，而较旧的一方没有理由判定它无效。但 `messageId` 里是一个数字就不是新协议；那是缺陷，而悄悄把它强制转换的消费方会掩盖该缺陷，直到它以更难诊断的形式浮现。

## 每种传输的回答方式相同 {#every-transport-answers-the-same-way}

这些规则约束的是协议，而不是线上格式。支持不止一种传输的消费方 MUST 对同一个事件作出同样的判定，无论它如何到达：如果一条流以 JSON 存活，它就 MUST 以 protobuf 存活；如果它失败，就 MUST 以同样的方式失败——除非二进制编码本身无法表达判定所依赖的那个差异，即本页下文指出的两种情形（无法命名的信封分支，以及被 protobuf 实体化的缺失）。

这给读取方可自行决定的范围划定了上限。把字节变成事件是读取方的全部职责——一个字节无法映射到任何事件的帧就是解码失败，这个判断本来就是读取方的分内事。但一个成功读取的事件是否携带实现所识别的东西则不然：那个问题属于每种传输都共享的唯一阶段。一个同时做验证的读取方会让自己的传输比其他传输严格得多，于是生产方对内容类型的选择就决定了运行能否存活。

二进制情形需要一处迁就。文本读取方可以传接一个未知类型的事件，因为类型以字符串形式传递，共享阶段可以按名字把它丢弃。二进制读取方做不到：一个它未按其编译的信封分支，没有名字可供传接。这样的帧 MUST 被丢弃，并带一条警告，而不是让运行失败——这正是共享阶段会给出的同样答案，只是为一个无法把问题推迟的传输写定下来。

!!! note
    一个二进制编码在它不给某个字段以"存在性"的地方，就无法遵守这一点。
      在 protobuf 中，这同时覆盖必需的标量和必需的列表：生产方省略的必需字符串
      到达时是空字符串，必需的数组到达时是空数组，而同一事件以 JSON 形式会被判定为
      畸形被拒绝，它们却被接受。模式本就禁止省略这些字段，所以这改变的是对一个有缺陷
      的生产方的诊断方式，而不是符合性生产方可发送的内容。

## 消费方如何处理不可识别的材料 {#what-a-consumer-does-with-unrecognised-material}

向应用代码暴露事件的消费方 MUST NOT 把不可识别的材料当作协议所描述的那样递送出去。已经读取了这些材料的消费方 MUST 做以下之一：

- **丢弃它**，如果整个事件都是不可识别的类型。消费方 SHOULD 发出警告并指明该类型。
- **剥离它**，如果它是某个否则有效的事件上的未知属性或不可识别的并集成员。
  消费方 SHOULD 发出警告并指明被移除的路径。

消费方 MUST NOT 让被剥离的属性存活到应用代码收到的值里，也 MUST NOT 让被丢弃的事件到达应用代码。

这仅在模式封闭了某个对象的地方适用，而模式描述协议自身对象之处皆是如此。在模式刻意让对象保持开放的地方，它没有描述的成员根本不是不可识别的材料，MUST 被保留。JSON Patch 操作就是这种情况：RFC 6902 第 4 节要求操作忽略它未定义的成员，而不是拒绝它们，所以携带了一个残余 `value` 的 `remove` 是合法的补丁，并且完整到达。在那里做剥离的消费方删除的是符合性数据，它发出的警告也不着边际。

这条规则约束的是管道，而不是解析器。只解析事件的库层——例如各 SDK 中生成的模型——刻意保留未知属性，以便它上面的中间件仍然能看到它们。一个提供这样的解析器却没有强制执行阶段的 SDK 尚未满足这条规则；目前那就是 Python 和 .NET，它们的模型宽松地解析，而在应用代码之前没有剥离的阶段。

!!! note
    有一种情形参考实现尚未做到：一个模式为封闭字符串值集合的字段——例如消息的 `role`——
      是作为叶子检查的，所以那里的不可识别值是致命的，而不是被剥离。.NET 转换器
      以同样的方式拒绝未知的 role 或 outcome。上面的规则是协议所要求的；两者都是
      相对它的缺口，而不是对它的软化。

剥离会一直深入到最底层，剥离掉什么取决于不可识别的值坐在哪里：

- 在**可选**位置：移除该字段，其周围的一切存活。
- 在**必需**位置：转而移除*包含*它的那个值。一个媒体部分的 source 是这种实现从未听说过的类型时，整个部分被移除——留下一个没有 source 的部分只会递给验证器一个它必须当作畸形处理的东西，把一次新增变成致命错误。
- 在**列表**内部：不可识别的元素被丢弃，列表存活。

## 中间件的位置 {#where-middleware-sits}

中间件——消费方安装的用于转换、观察或改写流的任何东西——MUST 在强制执行之前运行，且强制执行 MUST 在验证之前、在应用代码看到任何东西之前运行。

```
producer → compatibility boundary → middleware → enforcement
         → chunk expansion → verification → application
```

兼容性边界是对协议已退役形状的常开翻译器。它 MUST 最先看到流，因为退役形状可能是一个块，而比它更早遇到该形状的阶段要么会在它上面失败，要么会把它变成边界再也认不出来的东西。中间件*链* MAY 在自身阶段之间展开块，使每个阶段收到开始/内容/结束形式——参考实现的链式助手正是这么做。因此中间件 MUST 对两种形式都有准备：它看到什么取决于它坐在链中的哪个位置。

阶段之间的展开收窄了一项保证，而且这种收窄是明说的，不是隐藏的：展开合成的事件只携带协议所定义的东西，所以*块上的*不可识别字段只有在上述规范顺序下才能存活到强制执行——并赚到它的警告。一个提前展开的链会悄悄丢掉它们。符合性生产方从不发出这类字段，所以丢失的是来自较新协议版本的材料，它们正试图穿越一条提前展开的链。展开存在以传递的材料——增量、开头字段、元数据、`rawEvent`、归属——原封不动地传递；一个块的 `timestamp` 则不然，因为合成事件不是那个块，它与未知字段一样，只在规范顺序下、只在展开之前被判定。

块本身就是一个事件，MUST 被当作事件来判定：无论哪个阶段先遇到一个畸形的块——上述规范顺序下是强制执行，中间件链提前展开时则是展开——MUST 拒绝它而不是修复它，且 MUST NOT 对强制执行本会拒绝的畸形已知值做规范化、赋默认值或掩盖。一个为畸形 role 替换了默认值的消费方，使同一个生产方缺陷在被直发时是致命的、在被作为块发送时是隐形的，于是生产方碰巧使用的形式就决定了它的缺陷是否会被上报。

验证 MUST 在展开之后运行，因为它检查的东西——消息和调用在继续之前先开启、在继续之后关闭——只有在块变成它所代表的事件之后才存在。

这个顺序在两个方向上都是承重的：

- 中间件 MUST 在强制执行移除材料之前看到它。垫片的存在恰恰是为了转换当前协议没有描述的形状；如果强制执行先剥离了那个形状，垫片收到的就是一个无物可转换的事件，运行会丢失无人能恢复的数据。
- 应用代码 MUST NOT 看到强制执行本会移除的材料。翻译器有了它们的机会之后，仍然不可识别的东西就是不可识别的，并且到此为止。

消费方 MUST 在每条为应用代码产生事件的路径上应用此顺序，包括重连和重放。一条跳过强制执行的路径是保证上的一个洞，而不是优化。

## 出站材料 {#outgoing-material}

同样的边界适用于消费方所发送的东西。在传输之前，消费方 MUST 从运行输入中移除不可识别的材料，SHOULD 就所移除的内容发出警告，并在发送任何东西之前把畸形的已知字段当作致命的。

收到运行输入的生产方 MUST 对它应用同样的不对称性：不可识别的材料不使输入无效，畸形的已知字段才会。

## 生产方不得做什么 {#what-a-producer-must-not-do}

生产方 MUST NOT 发出协议未描述的事件类型，并指望消费方会忽略它。不可识别事件得以存活，是为了让协议能够新增它们，而不是为了让生产方通过事件流走私私有信令；`CUSTOM` 和 `RAW` 正是为此而存在，且由模式描述。
