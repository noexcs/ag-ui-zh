<em class="lead">智能体在运行之前关于自身声明了什么、一项声明要求什么、以及它不要求什么</em>

一次运行向消费方展示智能体*做了什么*。能力让消费方在要求智能体做任何事之前，先了解它*能做什么*：它是否流式输出推理、是否会暂停等待批准、接受哪些模态、可以向哪些子智能体委托。应用利用它们来塑造所提供的界面——只在接受文件的地方提供文件选择器，只在支持中断的地方提供批准入口——而不是靠试探来发现支持情况。

[模式](../schema.md#agentcapabilities)定义了它的形状：`AgentCapabilities`，一组 OPTIONAL 的组，每组都是 OPTIONAL 字段的对象。本页说明一项声明要求什么。它刻意不规定消费方如何*获取*声明——见[获取](#retrieval)。

## 声明 {#declaring}

每一个组，以及组内的每一个字段，都是 OPTIONAL。生产方声明它有话说的事，省略其余部分。字段所引用的记录保留它们自身的要求：`SubagentInfo` 需要其 `name`，`tools.items` 中的条目是一个 `Tool`。

**被省略的字段意味着未声明，而非不受支持。** 对 `reasoning` 只字未提的智能体，并没有说它不能推理；消费方 MUST NOT 从声明的缺失推断出能力的缺失。当智能体想要声明某项*不受支持*时，布尔字段正是为此而存在，用来显式承载 `false`。

生产方 SHOULD 只声明它实际做的事。声明是对应用关于如何为一次运行做准备的陈述；一个智能体不遵守的声明会误导建立在它之上的界面。没有义务声明所有为真的事——最小声明是符合性的——但声明了的内容 SHOULD 成立。

声明是告知性的，不具有约束力。事件流才是权威：消费方 MUST NOT 因为到达了一个声明未预料到的事件、或因为某项已声明的能力未被行使，就拒绝一条流或把一次运行当作失败。一个在 `reasoning: { supported: false }` 之下发出推理事件的运行，其生产方值得被投诉，而不是其流值得被拒绝。

## 各组 {#the-groups}

各组划分了协议的特性。当某个组描述的是一族事件时，那一族事件的页面管辖事件本身的要求；声明只是对它们的预先说明。

| 组            | 声明内容                                                                                         | 由谁管辖                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| `identity`       | 名称、框架、版本、提供方、文档，以及一个开放的 `metadata` 对象                 | 本页                                                            |
| `transport`      | 智能体提供服务的[传输绑定](../basic/transports/index.md)                        | [传输](../basic/transports/index.md)                           |
| `tools`          | 智能体是否调用工具、它所*提供*的工具，以及是否接受应用的工具 | [工具调用](../events/tool-calls.md)                          |
| `output`         | 结构化输出和可产出的 MIME 类型                                                      | —                                                                    |
| `state`          | 快照、增量、跨运行的持久化、长期记忆                                     | [状态](../events/state.md)                                    |
| `multiAgent`     | 委托、交接，以及它可调用的 `subagents`                                          | [子智能体](../events/subagents.md)                            |
| `reasoning`      | 推理是否被发出、流式输出或加密                                             | [推理](../events/reasoning.md)                            |
| `multimodal`     | 作为 `input` 接受的模态，以及作为 `output` 产出的模态                                          | `input` 见[运行输入](../basic/run-input.md#messages)；`output` 见备注 |
| `execution`      | 代码执行、沙箱化、迭代与时间限制                                            | —                                                                    |
| `humanInTheLoop` | 批准、干预、反馈，以及参与中断–恢复                        | [中断与恢复](../basic/patterns/interrupt-resume.md) |
| `custom`         | 标准组未涵盖的任何内容                                                        | —                                                                    |

有些字段值得在模式中的描述之外再加一条备注。

`output.structuredOutput` 声明智能体能按某个模式塑造其回答，但本协议的这个版本没有可供消费方提供该模式的字段，也没有把输出标识为结构化的事件。该声明告诉应用智能体有此能力；模式如何到达智能体、塑造后的回答如何返回，都是集成特有的事，消费方 MUST NOT 期望某个标准事件来承载其中任何一个。

`multimodal.output` 声明智能体能够*产出*什么，但本协议的这个版本没有定义图像或音频输出：助手消息内容和 `TEXT_MESSAGE_CONTENT` 增量都是文本。该声明是面向应用的——应用可能经由集成特有的通道收到此类输出——本规范的任何地方都没有说它如何传递。消费方 MUST NOT 期望某个标准事件来承载它。

`tools.items` 列出*智能体*提供的工具——它自己的函数、搜索、代码执行——与 `RunAgentInput.tools` 不同，后者携带*应用*为某次运行提供的工具。两者永不相合：智能体自己的工具不是供应用执行的，应用的工具也不在这里声明。

`multiAgent.subagents` 为选择界面而命名智能体可调用的子智能体。它是定义列表，不是调用列表：消费方在线上遇到的标识符是 `subagentRunId` 值，每次调用一个，在运行时签发——[子智能体](../events/subagents.md) 管辖它们，本页的任何内容都不对它们作预测。

两个 `transport` 标志同样描述了这个版本未定义的机制。`transport.resumable` 说的是按序列号恢复被中断的流，`transport.pushNotifications` 说的是运行结束后的投递；两个[HTTP 绑定](../basic/transports/index.md)都不携带序列号，都不恢复流，也不定义运行后的通道。智能体 MAY 为自己的一种传输声明它们；消费方 MUST NOT 期望任何标准绑定来遵守它们。

## `identity.metadata` 与 `custom` {#identity-metadata-and-custom}

两个开放对象承载标准字段所不承载的内容。`identity.metadata` 是协议的[元数据](../basic/metadata.md)形状——按键开放，一个键下可以是任何 JSON 值——用于集成特有的身份信息。`custom` 是为不属于任何标准组的能力而设的逃生口。两者都按键开放：消费方 MUST 保留其中它不认识的内容，而不是剥离它，与别处的元数据完全一致。协议对两者都不附加含义。

## 获取 {#retrieval}

本规范定义了声明的形状及其要求。它不定义消费方如何获取声明。这个版本的任何传输绑定都不承载能力交换，本页也不创造这样一个机制：智能体的能力是从客户端智能体对象上的某个方法读取、从应用定义的端点获取、还是静态配置的，是实现的自有之事。

这是刻意为之。发现协议比声明形状是更大的承诺，而没有它，形状本身也有用。以任何方式暴露能力的实现 MUST 对能力使用这个形状。

## 错误处理 {#error-handling}

能力对象不经过事件管道承载，因此[处理模型](../basic/processing.md)的剥离义务不适用于它；该模型在*不可识别*与*畸形*之间所作的区分则适用。不可识别的成员——本版本未定义的组或字段——是严格层的事，不是消费方的事：模式对每个能力对象都是封闭的，因此这样的文档无法通过对其的验证，但消费方 MUST NOT 因为声明携带了它们就拒绝该声明，于是较新智能体的声明不会在较旧的消费方处被弹回。能力不经过事件管道的强制执行阶段，因此消费方保留还是丢弃不可识别的成员是实现的自有之事，符合性实现之间并不一致。一个已知字段携带了模式所拒绝的值——该为布尔的地方是字符串——属于畸形，消费方 MUST NOT 使用它无法验证的声明。

由于声明是告知性的，被拒绝的或缺失的声明 MUST NOT 妨碍一次运行。无法获取或验证智能体能力的消费方，按智能体什么也没声明来处理。
