<em class="lead">AG-UI 协议的行为规范</em>

AG-UI 是一个开放协议，用于标准化智能体与面向用户的应用之间的交互：一个请求进，
一条有序的类型化事件流出，承载用户从智能体看到的一切——文本、工具调用、推理、
共享状态、进度。

本规范基于 [`schema.json`](schema.json) 中的 JSON Schema，定义了权威的协议
要求，并以可读的形式呈现为 [Schema 参考](schema.md)。

如需实现指南、概念与示例，请参阅[文档](https://docs.ag-ui.com/introduction)。

本文档中的 “MUST”、“MUST NOT”、“REQUIRED”、“SHALL”、“SHALL NOT”、“SHOULD”、
“SHOULD NOT”、“RECOMMENDED”、“NOT RECOMMENDED”、“MAY” 和 “OPTIONAL” 这些关键字，
当且仅当它们以全部大写字母出现（如本段所示）时，须按
[BCP 14](https://datatracker.ietf.org/doc/html/bcp14)、
[[RFC2119](https://datatracker.ietf.org/doc/html/rfc2119)] 和
[[RFC8174](https://datatracker.ietf.org/doc/html/rfc8174)] 中的描述来解释。

## 本文档是什么 {#what-this-document-is}

JSON Schema 说明事件长什么样。它无法说明事件可以以什么顺序到达、实现在遇到
不认识的内容时该怎么办、或何时必须发出警告。这些规则就是协议，本文档陈述
了它们。

权限的划分是刻意的、绝对的：

- **[模式](schema.md) 对结构具有权威。**
  哪些字段存在、哪些是必需的、每个字段承载什么类型、判别字段可以取哪些值。
  本文档提及某个字段时，是为了赋予规则以含义——绝不重述字段的形状。
  若两者在结构上有分歧，以模式为准，且本文档存在 bug。
- **本文档对行为具有权威。**
  顺序、生命周期、归属、错误处理、兼容性。模式无法表达其中任何一项。
  若某个实现与这里的某条规则相抵触，则该实现有 bug。

## 角色 {#roles}

每条规则都指明它约束谁。两个角色承担义务：

- **生产方** 是发出事件流的一方——一个智能体、一个代理、一个桥接器、一个
  测试替身。
- **消费方** 是读取事件流的一方——一个客户端 SDK、一个 UI、一个记录器、
  另一个代理。

同时承担两种角色的参与者受两组规则约束，且在每个方向上分别适用。

## 符合性 {#conformance}

当一个实现满足适用于其所扮演角色的所有 MUST 与 MUST NOT 时，即视为符合。
SHOULD 级别的规则描述良好实现的做法；偏离其中一条是一个需要理由的决定，
而非违规。

符合性按事件流逐条判定。发出过一次畸形运行的生产方即为不符合，无论它在
其他运行中表现如何。

## 概述 {#overview}

协议分解为每个实现都要支持的基础部分，以及生产方在有内容可说时发出的特性：

- **[事件模型](basic/index.md)** — 信封、通用字段、标识符。
- **[运行输入](basic/run-input.md)** — 唯一一条从应用流向智能体的消息。
- **[元数据](basic/metadata.md)** — 附着于一切上的开放通道，以及它的合并方式。
- **[事件模式](basic/patterns/index.md)** — 流式、快照–增量、中断–恢复。
- **[传输](basic/transports/index.md)** — HTTP + SSE、HTTP + Protobuf，以及自定义
  传输绑定必须满足的契约。
- **[处理模型](basic/processing.md)** — 中间件先于强制执行；未识别的材料存活，
  畸形的已知值是致命的。
- **[版本化与兼容性](basic/versioning.md)** — 与更旧或更新的通信方打交道，
  以及丢失内容所带来的义务。
- **[事件流](events/index.md)** — 八个事件族。

## 安全与信任安全 {#security-and-trust-&amp;-safety}

AG-UI 将模型输出转化为应用的行为：工具调用变成动作，状态事件变成写入，
流式内容变成用户阅读的内容。随之而来的是协议无法在线上层面强制执行、
但实现方必须处理的义务。

### 关键原则 {#key-principles}

1. **用户同意与控制。** 应用决定什么被运行。在执行有副作用的
   [工具调用](events/tool-calls.md) 之前，它 SHOULD 获得用户的明确同意，
   且 MUST NOT 将一个未经用户批准的动作表示为已获用户批准。
2. **模型输出是不可信的输入。** 工具参数、工具结果、
   [状态](events/state.md) 内容和[透传](events/passthrough.md) 载荷跨越
   信任边界。应用 MUST 验证其所依据的内容，MUST NOT 将流式内容渲染为
   可执行的标记。
3. **数据双向流动。** 状态和消息在每次运行中都往返经过消费方。生产方
   SHOULD NOT 在其中放置机密信息；消费方 SHOULD 将推理和加密产物与
   对话同等保密地对待。

### 实现指南 {#implementation-guidelines}

协议本身无法强制执行这些原则。实现方 SHOULD 为有重大后果的动作构建同意
流程，在每个信任边界上验证模式与语义，将渲染与执行隔离，并记录足够的
日志以审计智能体代表用户做了什么。

## 范围 {#scope}

本文档规定协议本身：事件流、运行输入，以及交换它们的各方所承担的义务。
它不规定任何特定集成在收到事件后如何处理该事件、智能体框架应如何构建、
或 UI 应如何渲染任何内容。

AG-UI 与三个第一方 SDK 一同维护——TypeScript、Python 和 .NET——这里的
每条规则同等适用于它们。其他语言的绑定由社区维护；当它们声明符合性时
受本文档约束，但本文档中的内容均不源于它们。
